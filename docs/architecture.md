# Архитектура и границы этапа 1

## Источник данных

Единственный источник общих данных — Supabase PostgreSQL. Auth управляет пользователями и сессиями. `profiles` хранит отображаемое имя, `families` — пространства, `family_members` — роли, `family_invitations` — хеши одноразовых кодов, `family_preferences` — приватные предпочтения, `family_activity` — журнал управления пространством. Все семейные данные имеют внешний ключ `family_id`. Ни локальный кэш, ни клиентская метадата пользователя не определяют роль.

Состояние интерфейса хранится в React, тема — в localStorage. Сессия хранится Supabase SDK. Публичные Auth-маршруты не требуют текущей семьи. Клиентские env-переменные проверяются до создания клиента. При отсутствии Supabase показывается инструкция; запись данных не заменяется localStorage.

## Доступ

RLS включён на всех таблицах. Прямые записи в семьи, членство, приглашения и журнал запрещены клиентским ролям. Изменения выполняются RPC `create_family`, `create_invitation`, `join_family`, `manage_member`, `revoke_invitations`, которые проверяют `auth.uid()` и роль. `SECURITY DEFINER` функции фиксируют пустой `search_path`, используют полные имена и недоступны `anon` / `PUBLIC`. Проверки членства выполняются в закрытых функциях, чтобы исключить рекурсию политик.

Приглашение не даёт роль владельца, действует 7 дней и потребляется в транзакции под блокировкой строки. В БД сохраняется SHA-256; исходный код показывается создателю один раз и не кладётся в URL/логи/хранилище браузера. Семейные роли проверяются сервером. Удаление участника не удаляет историю. Изменения ролей сериализуются блокировкой семьи; менять владельца нельзя.

Будущие операции редактирования должны проверять `can_edit_family(family_id)`. Само по себе присутствие кнопки в интерфейсе не означает право доступа. Семейные предпочтения на этапе 1 доступны только их автору; перед отправкой внешнему ИИ потребуется отдельное согласие. В текущем коде внешних ИИ-запросов нет.

Realtime дополняется обновлением при фокусе/восстановлении связи и периодическим запросом. Будущие счётчики не отображаются фиктивными нулями; `—` означает, что соответствующий модуль ещё не подключён. Браузерные тесты без ключей проверяют состояние настройки; для реальной Auth-интеграции требуется подключённый Supabase.

## Дальнейшие этапы

Новые таблицы добавляются миграциями вместе с работающим модулем, а не заранее как независимые пустые структуры.

Для количеств и финансов: PostgreSQL `numeric`, целочисленные копейки либо десятичная арифметика в клиенте, нормализованные продукты и совместимые единицы. Закупка/списание/заготовка — серверные транзакции с уникальным ключом идемпотентности, блокировкой партий, запретом отрицательных остатков и неизменяемым журналом движений. Покупка создаёт расход и партию ровно один раз; использование готовой заготовки не списывает ингредиенты повторно. Рецепты, на которые ссылается история, архивируются. Эти сценарии ещё не реализованы на этапе 1.

## Эксплуатация

Нужны отдельные Supabase-проекты для разработки и production, HTTPS, корректные Auth Redirect URLs, собственный SMTP перед публичным запуском и резервные копии. Service worker не кэширует запросы Supabase или персональные данные. Обновления оболочки применяются автоматически; формы содержат только небольшие операции, без офлайн-очереди. Не включайте кэширование будущих чувствительных данных без очистки при смене пользователя.
