# Этап 2. Книга рецептов

## Включение в существующем проекте

Основа этапа 1 используется без замены. Новых внешних ключей и сервисов, кроме уже подключённого Supabase, не нужно.

1. Если основа ещё не настроена, выполните шаги Auth/семейного пространства из README и примените `202610280001_foundation.sql` один раз.
2. В **Supabase → SQL Editor** выполните **целиком** `supabase/migrations/202610280002_recipes.sql` один раз. Альтернатива для проекта с корректной историей CLI-миграций: `supabase db push`. Не запускайте foundation повторно поверх существующих таблиц; при первоначальной ручной настройке используйте SQL Editor и для второй миграции.
3. Миграция создаст `recipe_categories`, `recipes`, `recipe_ingredients`, `recipe_steps`, `recipe_favorites`, `recipe_photos`, индексы, RLS и RPC. Категории — справочник, а не демонстрационные рецепты.
4. Бакет `recipe-photos` создаётся **приватным**, с лимитом 5 МБ и MIME `image/jpeg`. Не делайте его публичным. Клиент оптимизирует JPEG/PNG/WebP до JPEG, 1600 пикселей по длинной стороне; исходный файл — до 20 МБ. HEIC нужно предварительно преобразовать в JPEG.
5. Переменные `VITE_SUPABASE_URL` и `VITE_SUPABASE_ANON_KEY` остаются прежними. На GitHub Pages они задаются в **Settings → Secrets and variables → Actions → Variables**. Если их меняли — перезапустите «Публикация веб-версии». Секретный `service_role` в браузере запрещён.
6. Войдите взрослым участником семьи и откройте «Рецепты». Создайте рецепт, добавьте фото, сохраните. Откройте его на другом устройстве, проверьте редактирование, избранное, архивирование и семейную изоляцию. Этот шаг с вашим реальным Supabase ещё не выполнен в облачной среде — в неё не переданы параметры/доступ к вашей БД.

Применение SQL не выполняется при каждой сборке: публикация сайта не имеет административного доступа к Supabase. Код может быть опубликован до миграции; в этом случае раздел покажет инструкцию/ошибку подключения, а остальные разделы продолжат работать.

## Реализованное поведение

- Карточки и компактный список: название, категория, суммарное время, порции, фото, избранное.
- Поиск по названию и ингредиентам, 12 категорий и избранное; сортировки по дате (новые первыми), названию, времени и популярности (числу открытий).
- Форма: описание, категория, подготовка/готовка, порции, сложность, произвольное число ингредиентов и шагов; строки можно добавлять/удалять, шаги переставлять. Все поля хранения, источник, заметки, избранное, фото блюда и шагов сохраняются.
- Подсказки ингредиентов берутся из уже сохранённых семейных рецептов. Отдельного каталога продуктов пока нет: он относится к этапу 4.
- Пересчёт порций — только отображение. Исходные значения не меняются. «По вкусу» не умножается; дробные количества показываются с точностью до 4 знаков, через русскую запятую. В БД количество — `numeric(14,4)`.
- Избранное персональное для текущего пользователя и сохраняется в БД. Ребёнок может читать семейные рецепты и сохранять личное избранное. Редактирование доступно владельцу/взрослому либо ребёнку, которому владелец дал право редактирования.
- Меню, план готовки, покупки и заготовки пока не реализованы. Соответствующие кнопки сообщают об этом и не создают фиктивных записей. Импорт по фото/видео/ссылке/тексту также честно сообщает об отсутствии ИИ; ручная форма и загрузка фото полностью независимы от ИИ.

## Согласованность и безопасность

`save_recipe` сохраняет основную запись, ингредиенты, упорядоченные шаги, метаданные фотографий и личное избранное **в одной транзакции**. Записи изменяются только через RPC, прямые клиентские INSERT/UPDATE/DELETE закрыты. Изоляция чтения обеспечивается RLS на всех таблицах. `get_recipe_page` выполняется с правами вызывающего пользователя и возвращает JSONB-пакеты по 200 рецептов: ограничение PostgREST не обрезает массивы ингредиентов и шагов. Клиент получает все страницы, в том числе избранного.

Версия рецепта проверяется под блокировкой строки. Устаревшее сохранение/удаление отклоняется с понятным сообщением, а форма и черновик сохраняют введённый текст. Просмотры не меняют версию содержимого. Автоматического объединения конфликтующих правок нет: сохраните нужный текст и откройте актуальную версию.

Фотографии загружаются перед транзакцией под случайными именами `<family_id>/<recipe_id>/<uuid>.jpg`. RPC проверяет принадлежность пути и существование объекта в Storage. При ошибке новые неиспользованные загрузки очищаются; при замене/удалении старые непривязанные файлы также очищаются. Storage policy запрещает удалять файлы, на которые ссылается `recipe_photos`, в том числе если ответ об успешном сохранении потерялся в сети. PostgreSQL и Storage не являются одной распределённой транзакцией: при обрыве браузера/сети возможны приватные непривязанные файлы. При обслуживании можно удалять старые объекты без строки `recipe_photos`, предварительно убедившись, что загрузка не выполняется. Никогда не удаляйте объекты активных или архивных рецептов по одному возрасту файла.

Для показа фото выдаётся подписанная ссылка на 15 минут и обновляется при открытом экране. Отзыв членства не отзывает уже выданный URL мгновенно: он перестаёт работать по истечении срока. Бакет никогда не становится публичным.

«Удалить» устанавливает `deleted_at`, увеличивает версию и убирает рецепт из активной книги. Запись, ингредиенты, шаги, избранное и приватные фото сохраняются для будущих ссылок меню и истории. Интерфейс восстановления архива не входит в этот этап. Архив читается только членами семьи через RLS.

Realtime обновляет книгу при изменениях рецептов/избранного. Есть обновление при фокусе, восстановлении сети и раз в минуту; это также страхует ограничения событий удаления Supabase Realtime. Редактируемая форма не заменяется автоматически новыми серверными полями — конфликт определяется при сохранении.

## Черновики

Поля и оптимизированные фото автоматически сохраняются в IndexedDB через 500 мс после изменений. Ключ включает пользователя, семью и рецепт; чужому аккаунту черновики в интерфейсе не показываются. Черновик локален для браузера, не заменяет рецепт в БД и не синхронизируется между устройствами. Выйти из формы/аккаунта или закрыть вкладку с несохранёнными изменениями можно после предупреждения. При подтверждённом уходе черновик остаётся, при успешном сохранении или явном удалении — очищается. Исходная версия сохраняется вместе с черновиком для обнаружения конфликта.

На общем устройстве используйте отдельный профиль браузера: локальные черновики содержат личный текст и выбранные изображения. В приватном режиме или при заполненном хранилище браузер может запретить черновики; форма сообщает об ошибке. Сохранение рецептов требует сети. Полной офлайн-очереди/офлайн-книги ещё нет (этап 7).

## Проверки

```sh
npm run typecheck
npm test
PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH=/usr/bin/chromium npm run test:ui
PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH=/usr/bin/chromium npm run test:pages
```

Последние две команды запускайте последовательно: они используют один `dist`. Если системного Chromium нет, выполните `npx playwright install chromium` и уберите переменную пути. Каждая браузерная команда также проверяет production-сборку.

- Модель: валидация, единицы, точность, пересчёт, поиск/фильтры/сортировки и порядок шагов.
- PostgreSQL/PGlite: обе миграции, транзакции, CRUD, версии, любимые рецепты, детские права, семейная изоляция, запрет прямой записи и приватные Storage-политики на тестовых `storage.buckets/objects`.
- Браузер: полный цикл формы на компьютере/телефоне, сжатие и замена/удаление фото, черновик с фото после перезагрузки, предупреждение при уходе, избранное/поиск, подтверждение удаления, конфликт версий, обработка неудачного сохранения, доступ ребёнка и сообщения о будущих разделах.
- GitHub Pages: подпапка, прямые ссылки, Auth callback и PWA.

В браузерных тестах HTTP-контракт Supabase перехватывается тестовой обвязкой и исполняет реальные SQL-миграции через PGlite. Пользовательские записи тестов существуют только в изолированных тестовых БД. Это проверяет UI и SQL вместе, но **не является проверкой реального Supabase Auth/Storage, доставки писем и межустройственной связи**. Настоящую интеграцию проверьте по шагу 6 после применения миграции в вашем проекте.
