# Подключение расширенной «Моей кухни»

## Миграции Supabase

В этой сессии SQL проверялся в PGlite (PostgreSQL/WASM), но в ваш реальный проект Supabase не применялся: административный доступ в среду не передан. Публикация GitHub Pages не запускает миграции базы.

Если первые две миграции уже успешно выполнены, не повторяйте их. В Supabase SQL Editor запускайте новые файлы целиком и по очереди:

1. `202610290003_planning.sql` — меню/задачи/факты готовки и общая основа запасов, заготовок и журнала операций.
2. `202610290004_inventory.sql` — складские операции, использование заготовок, приватное хранилище их фото.
3. `202610290005_shopping_budget.sql` — потребности, покупки, расходы, компенсации и бюджет.
4. `202610290006_assistant.sql` — очередь серверных ИИ-запросов и явное принятие предложений.
5. `202610290007_notifications.sql` — персональные напоминания и настройки.
6. `202610290008_sync_guards.sql` — дополнительные проверки версий/интеграций для очереди и связей рецептов.

Для пустого проекта сначала выполните `202610280001_foundation.sql` и `202610280002_recipes.sql`. Для проектов, чья история миграций ведётся Supabase CLI, используйте `supabase db push`. Не смешивайте ручной повтор уже применённого SQL и CLI без согласованной истории миграций. Миграции аддитивны, не очищают пользовательские таблицы и не загружают демонстрационные блюда/остатки. Четыре места хранения — справочник, как категории рецептов.

Браузеру нужны прежние публичные `VITE_SUPABASE_URL` и `VITE_SUPABASE_ANON_KEY`. При GitHub Pages они остаются Repository Variables в Actions. Серверный service*role, ключ провайдера и пароль БД не должны находиться в VITE*\* или Git. После изменения Variables перезапустите «Публикация веб-версии». Код обновляется автоматически после push в main; успешную публикацию смотрите в Actions.

## Критические операции

`kitchen_mutate(family, key, action, data)` сначала блокирует семью, проверяет право редактирования и идентификатор операции, затем выполняет весь набор записей в одной транзакции. Дубликат с тем же ключом/содержимым получает прежний результат; другой payload с тем же ключом отклоняется. При ошибке ни остатки, ни деньги, ни история не меняются. Прямые клиентские записи в общие таблицы закрыты.

- Расход ингредиентов группируется по точному нормализованному названию и совместимой единице. Нормализация убирает лишние пробелы/регистр, а не объединяет похожие продукты. Только кг→г и л→мл имеют автоматические коэффициенты. Стаканы и граммы не смешиваются.
- Выбираются непросроченные партии по ближайшему сроку (FEFO). Недостаток откатывает готовку целиком. Пользователь подтверждает фактический расход, включая явные нули для неиспользованных ингредиентов.
- Число порций уже включает предназначенные для заготовок порции. При подтверждении фактические порции распределяются между съеденным/холодильником/морозилкой; сумма должна совпасть. Даты годности задаёт пользователь, они не выдумываются.
- Покупка создаёт одну партию фактического количества, один расход и журнал. При отмене создаются компенсации с сохранением истории. Если покупка уже частично использована, отмена отклоняется, чтобы не уйти в минус.
- Использование заготовки уменьшает только её остаток и сохраняет факт использования. Повторного расхода ингредиентов нет. Привязка использования к меню — явный выбор пользователя, а не пересчёт штук в порции без коэффициента.
- `numeric` хранит точные количества и деньги; суммы бюджета агрегируются в PostgreSQL по журналу. Прогноз — пропорция расходов текущего месяца по прошедшим дням, без обещаний будущих цен.
- План, задача, партия, заготовка, расход и бюджет имеют версии. Устаревшая правка отклоняется. Журналы не удаляются при нулевых остатках и корректировках.
- Снимки рецептов в планах и фактах защищают историю после изменения оригинала. Политика Storage дополнительно защищает фотографии, использующиеся этими снимками.

## ИИ: подготовлен, но платный провайдер не включён

Алгоритмический подбор по запасам работает отдельно и подписан как расчёт, а не ответ ИИ. Настоящие запросы требуют Edge Function и отдельного решения владельца о расходах. В этой сессии платный провайдер не подключался и реальных ИИ-запросов не было.

После согласования стоимости/лимитов:

1. Разверните `supabase/functions/kitchen-assistant` командой `supabase functions deploy kitchen-assistant --no-verify-jwt`. JWT проверяется самим обработчиком через `auth.getUser()`; отсутствие gateway-проверки не открывает анонимный доступ.
2. Через защищённые Supabase Secrets задайте `AI_PROVIDER_KEY`, выбранный `AI_MODEL`, `APP_ORIGIN=https://ksuivash98.github.io`. Ключ — только на сервере. Автоматически доступные `SUPABASE_URL`, `SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY` использует среда Edge Functions; service_role нужен только серверу для сохранения результата и чтения явно разрешённых предпочтений.
3. Только после проверки тарифа установите `AI_ENABLED=true`. Пока значение отсутствует/false, обработчик отвечает «ИИ не активирован», не вызывая провайдера. Пример имён — в `supabase/functions/kitchen-assistant/.env.example`; реальные значения туда не записывайте.
4. Проверьте небольшой запрос взрослым участником. Квота учитывает также неудачные запросы. Ответ ограничен 4000 токенами и 100 предложениями; есть timeout. Контекст ограничен размером: большую книгу/запасы пока нужно уменьшить для запроса. Сервер не пишет меню без отдельного принятия.
5. Каждый участник управляет собственным согласием. Медицинские/пищевые ограничения не предполагаются автоматически. Предпочтения передаются только согласившихся авторов и при явном выборе использования предпочтений. Отзыв согласия прекращает будущую передачу, но не отзывает уже отправленный провайдеру запрос.

Проверены формат запроса и валидация ответов через тестовый fetch, серверный TypeScript — через Deno. Не проверены реальный платный провайдер, лимиты конкретной модели, SMTP и реальная межустройственная доставка Supabase Realtime. Импорт фото/текста добавлен отдельным обновлением (миграция 009 и функция recipe-import), но требует серверной настройки; [инструкция](recipe-import.md). Видео и ссылки ещё не реализованы. Не выдавайте это за завершённую ИИ-систему.

## Уведомления

Внутренние напоминания сохраняются в БД адресата: сроки партий/заготовок, готовка, покупки и изменения общего списка. Настройки персональны. Системное разрешение браузера запрашивается только отдельной кнопкой. Есть атомарное получение новых уведомлений, предотвращающее повторную выдачу одному аккаунту.

Доставка выполняется при открытом приложении. Фоновые Web Push/cron/VAPID при закрытом сайте не реализованы. На iOS возможность системных уведомлений зависит от версии и установки PWA; физические Android/iPhone в этой среде недоступны. Сообщения внутри приложения доступны независимо от системного разрешения.

## Офлайн

IndexedDB хранит отдельные копии для user_id/family_id: рецепты, меню, покупки и данные ранее открытых разделов. Срок копии — 24 часа; фотографии — не более 20 последних файлов, в отдельном персональном кэше, без общих Service Worker-кэшей API. Секреты и подписанные URL в этот кэш не записываются. Кэш и очередь аккаунта очищаются при выходе; отдельные черновики рецептов остаются в своём пространстве автора, как указано в предупреждении формы.

Офлайн разрешена очередь правок меню, задач и личного избранного. Черновики рецептов с фото сохраняются отдельно; готовые рецепты с файлами офлайн на сервер не отправляются. Запасы, покупки, деньги, подтверждение готовки и ИИ требуют сети. Очередь отображается как локальная, не как подтверждённая сервером.

При восстановлении сети повторно проверяются текущая сессия, членство и серверные версии. Ошибка/конфликт не удаляет текст и не перезаписывает актуальные данные. Пользователь видит локальный payload и может убрать операцию после сохранения нужного текста. Автоматического объединения конфликтов нет. Без актуальной сессии, свежего кэша или ранее открытого раздела офлайн-доступ не обещается. Отозванный доступ невозможно обнаружить без сети мгновенно; после восстановления он проверяется, общий кэш семьи очищается. На общем устройстве используйте отдельный профиль браузера.

## Обновление 011 — категории покупок

Один раз примените `supabase/migrations/202610310011_shopping_categories.sql` после предыдущих миграций через SQL Editor либо штатный CLI для базы с историей миграций. GitHub Pages SQL автоматически не выполняет.

В «Покупках» → «Изменить / удалить» и при ручном добавлении появилась «Категория». Выбор конкретной категории сохраняет её для продукта и всех его открытых покупок, включая явное «Другое»; пересчёт списка этот выбор не сбрасывает. «Категория продукта / автоматически» использует сохранённую категорию продукта, а для автоматических продуктов — словарь известных названий. Неизвестные и неоднозначные названия остаются в «Другом», платного ИИ нет.

Миграция уточняет прежнее «Другое» у знакомых продуктов и синхронизирует открытые позиции. Ранее выбранные категории, отличные от «Другое», сохраняются. Отличить старое ручное «Другое» от прежнего значения по умолчанию невозможно; при необходимости выберите «Другое» в новой форме, и оно закрепится. Оплаченные покупки, расходы, финансовые движения, количества и остатки не пересчитываются. Обновление категории увеличивает версии затронутых открытых позиций, чтобы устаревшая форма не перезаписала новое значение.


## «Мои продукты»: название и запас — разные записи

«Создать продукт» задаёт название, категорию и единицу учёта. «Добавить запас» указывает количество конкретной упаковки, дату покупки, срок годности и место хранения. Для разных сроков или мест создавайте отдельные запасы одного продукта. «Изменить запас» требует нового оставшегося количества, а не величины расхода: было 800 г, потратили 300 г — вводите 500 г. Остаток 0 убирает запас из активного списка, сохраняя историю. «Настройки продукта» меняют общие параметры названия, а не количество упаковки.

Кг и л пересчитываются в г и мл; упаковки в вес автоматически не переводятся. «Желаемый минимальный запас» пока является справочным значением и не влияет на расчёт покупок. Ручное внесение запаса не создаёт расход денег: покупку с ценой подтверждают в разделе «Покупки». В интерфейсе добавлены эти пояснения; новая миграция для них не нужна.

## Обновление 012 — очистка покупок

Один раз примените `supabase/migrations/202610310012_clear_shopping.sql` после предыдущих миграций через SQL Editor или штатный CLI для базы с историей миграций. Публикация GitHub Pages не применяет SQL.

Кнопка «Очистить покупки» отменяет позиции «Нужно купить» за выбранный месяц, включая все страницы списка, после отдельного подтверждения. Оплаченные покупки, расходы, запасы, меню и другие месяцы сохраняются. При новом расчёте по меню недостающие продукты могут появиться снова. Без сети или при пустом списке кнопка недоступна.

## Обновление 013 — очистка меню и плана приготовления

Один раз примените `supabase/migrations/202610310013_clear_planning.sql` после предыдущих миграций через SQL Editor или штатный CLI для базы с историей миграций. Публикация сайта не применяет SQL.

Кнопки «Очистить меню» и «Очистить план приготовления» после подтверждения отменяют незавершённые записи за выбранный месяц целиком, независимо от режима дня/недели/месяца и наличия даты у блюда в меню. Приготовленные записи, факты готовки, заготовки, запасы, покупки и другие месяцы остаются. Меню и задачи очищаются отдельно: очистка меню не отменяет связанные задачи, очистка задач не меняет меню. При необходимости выполните обе операции.

Отменённые записи скрыты по умолчанию; включите «Показывать отменённые», чтобы увидеть их и при необходимости изменить статус через обычную форму. Удаления строк из базы нет. Очистка работает только онлайн, проверяет семейные права, версии всех выбранных записей и повтор операции. При конфликте очистка откатывается целиком; обновите страницу и подтвердите заново. Новые записи с другого устройства, которых не было в подтверждении, сохраняются.

## Фильтры категорий и вид списков

В «Моих продуктах» и «Заготовках» категория, место хранения и поиск применяются вместе. Для сброса выберите «Все категории» / «Все места хранения» и очистите поиск. В «Покупках» и «Бюджете» фильтр категории меняет список позиций, но не месячные итоги, финансовую историю и область очистки. В меню и плане приготовления категория фильтрует только карточки. Ингредиенты рассчитываются для выбранного дня, недели (понедельник–воскресенье, включая дни соседнего месяца) или месяца. Переключение даты и стрелки навигации обновляют расчёт; блюда без даты не входят в день и неделю. Очистка по-прежнему относится ко всему месяцу; это указано рядом с управлением.

Переключатель «Плитка / Строки» доступен для рецептов, продуктов, заготовок, покупок, бюджета, меню, плана приготовления, блоков аналитики, семейных показателей главной, предложений помощника и уведомлений. Выбор хранится локально в браузере отдельно для каждого раздела и восстанавливается после перезагрузки. Если локальное хранилище недоступно, переключение продолжает работать до перезагрузки. В меню и плане переключатель открывает список за выбранный месяц; кнопки месяца/недели/дня по-прежнему открывают календарь. Таблицы отчётов и сами диаграммы сохраняют прежнюю структуру. Фильтры, переключение вида и изменение настроек отображения не меняют записи в Supabase; новая миграция не нужна.

## Компактные строки и календарь

В режиме «Строки» запасы, заготовки, покупки, расходы и записи планов размещают данные по горизонтальным колонкам. На узких экранах колонки переносятся; фото заготовки остаётся целиком видимым. Карточки показателей также используют строку для подписи и значения.

Высота дня календаря ограничена: длинный список блюд прокручивается внутри дня, заголовок с датой остаётся на месте. Область с блюдами доступна с клавиатуры. В календаре блюдо отображается одной строкой (название, порции, «⋯»), высотой 36 px на компьютере и 44 px на телефоне. Нажатие открывает полное название, приём пищи, дату, статус и прежние операции; в плане приготовления здесь же доступны шаги. В строках планов это окно открывает кнопка «Действия»; Escape закрывает его и возвращает фокус на кнопку. Расчёты, сохранение и статусы не менялись; миграция не требуется.

## Категории основных блюд

В рецептах и фильтрах добавлены «Мясные блюда», «Рыбные блюда», «Блюда с гарниром». Последняя категория предназначена для цельного рецепта основного блюда вместе с гарниром (например, плова или рыбы с картофелем); самостоятельные рис, картофель и овощи остаются в «Гарнирах». «Основные блюда» сохраняется для ранее сохранённых и пока не уточнённых рецептов. Массового переноса и угадывания категорий нет: категорию можно уточнить при редактировании рецепта.

Перед сохранением в новых категориях выполните в Supabase SQL Editor файл `supabase/migrations/202611010014_recipe_categories.sql`. Скрипт допускает повторный запуск: добавляет только недостающие строки справочника и сохраняет рецепты, версии, снимки меню и правила доступа. До применения при сохранении новой категории форма сообщает о миграции 014 и сохраняет введённые значения для повтора. Локальный и ИИ-импорт используют тот же список категорий; для обновления развёрнутого ИИ-импорта повторно опубликуйте Edge Function `recipe-import` (либо замените её код содержимым `supabase/dashboard/recipe-import.ts`).

## Несколько категорий рецепта

В форме рецепта можно отметить несколько категорий; нужна хотя бы одна. Все метки отображаются в карточке и просмотре. В книге рецептов кнопки категорий переключаются независимо. Когда выбрано несколько, «Совпадение категорий» позволяет показать рецепты с любой либо со всеми выбранными метками. Поиск, избранное и выбранная сортировка работают вместе с категориями. «Все рецепты» снимает категории и избранное, а «Сбросить фильтры» дополнительно очищает поиск. При изменении фильтров открывается первая страница результатов. Категории в меню и плане приготовления также учитывают дополнительные метки новых снимков; старые снимки сохраняют свою категорию.

После миграции 014 выполните в Supabase SQL Editor `supabase/migrations/202611010015_recipe_multiple_categories.sql`. Она добавляет массив категорий и переносит в него прежнюю категорию каждого рецепта без изменения версий. Новое сохранение выполняется атомарно через `save_recipe_with_categories`: прежние проверки семейных прав, версии и фотографий, сохранение инструкции по заморозке остаются в силе. Неизвестные, пустые и повторяющиеся метки не принимаются. Старые клиенты продолжают работать через прежние RPC и не стирают дополнительные метки при обычном редактировании. Старые локальные черновики и кэш с единственной категорией поддерживаются. До применения миграции сохранение нескольких меток показывает понятную ошибку; введённые значения остаются в форме для повтора.

## Редактор продуктов

В разделе «Продукты» кнопка «Редактор продуктов» открывает справочник, включая названия без запасов. Здесь можно искать по названию/категории, менять настройки, удалять из активного списка и восстанавливать через список «Удалённые». Удаление требует подтверждения и нулевого остатка во всех партиях: сначала используйте или спишите запасы. Продукт архивируется, поэтому партии, движения и финансовая история сохраняются; он больше не предлагается при добавлении нового запаса. Доступ зависит от семейного права редактирования, проверки остатков и версии также выполняются существующим серверным RPC. Новых миграций не требуется.

## Обновление открытого приложения

Новая оболочка проверяется при возвращении на вкладку, восстановлении сети и раз в минуту на видимом экране. Проверка service worker обходит HTTP-кэш. После установки новой версии перезагрузка откладывается, пока открыты форма/диалог или активно поле ввода; офлайн-данные и очередь не очищаются. Вкладку, открытую до добавления этой проверки, нужно один раз перезагрузить, чтобы получить новый механизм обновлений.

## Новый продукт из списка покупок

В «Покупках» → «Добавить вручную» можно найти существующий продукт по названию или нажать «Создать новый продукт». После «Создать и выбрать» название сохраняется в справочнике и выбирается автоматически; количество, единица и категория позиции остаются заполненными. Покупка добавляется в список только после итогового «Сохранить». Запас и расход денег при этом не создаются: они появятся при подтверждении фактической покупки. Пустой справочник не блокирует ручное добавление. Новых миграций не требуется.

## Поиск рецепта при планировании

В окне добавления или изменения блюда в меню и плане приготовления поле «Поиск рецепта» фильтрует список по названию без учёта регистра и различия е/ё. После ввода выберите рецепт из найденных. Если совпадений нет, сохранение блокируется до выбора доступного рецепта. Поиск не меняет дату, порции и примечания; ранее выбранный рецепт сохраняется при открытии редактирования. Новых миграций не требуется.

## Учёт продуктов и заготовок в ингредиентах плана

Таблица «Ингредиенты плана» в меню и плане приготовления учитывает продукты и заготовки с положительным непросроченным остатком. Очевидные варианты названий (е/ё, порядок слов, картошка/картофель, лук/репчатый лук, отварная курица/отварное куриное мясо) сопоставляются автоматически при совпадении единиц. Сырое и отварное, сухое и приготовленное не объединяются автоматически. Г/кг и мл/л приводятся к одной единице.

Кнопка «Подобрать все продукты» собирает предложения для всего списка выбранного периода. Очевидный единственный вариант уже выбран, неоднозначные варианты оставлены для уточнения. Применить готовый подбор можно одной кнопкой. Для отдельной корректировки в строке остаётся «Изменить источник». Для порций/упаковок и несовместимых единиц нужен явный коэффициент, например 800 мл в одной порции бульона. Один и тот же источник распределяется между строками без повторного зачёта. Просроченный, нулевой, удалённый или недоступный источник больше не участвует в расчёте; подтверждённый выбор не заменяется другим молча.

Сопоставления и коэффициенты — настройки расчёта, сохраняются в браузере отдельно по аккаунту и семье; их можно сбросить. Они не изменяют названия продуктов, остатки и историю. Подбор используется таблицей выбранного периода и пересчётом покупок на этом устройстве. Фактическое списание остаётся явной складской операцией. Схема и права Supabase не менялись, миграция не требуется.


## Общий подбор ингредиентов

Повторные названия и варианты порядка слов объединяются для подтверждения: одно соответствие используется во всех блюдах и при последующих открытиях на этом устройстве. Ранее сохранённые соответствия тоже переиспользуются; конфликтующие старые варианты не объединяются молча. Коэффициенты сохраняются для конкретной единицы измерения. Подтверждённый выбор и явный отказ от учёта не заменяются предложениями общего подбора. Для незнакомого пересчёта порций нужно указать вес/объём; сырые и отварные продукты не подставляются друг за друга заранее. Общий подбор применяется к таблице текущего периода и следующему пересчёту покупок; сам по себе складские записи и сохранённые строки покупок не меняет.


## Единый расчёт меню и покупок

«Рассчитать недостающие продукты» использует общий с таблицей меню расчёт: непросроченные запасы, заготовки и сохранённые в этом браузере соответствия/коэффициенты. При «Докупить: 0» автоматическая строка не нужна. Старые автоматические позиции обновляются или отменяются при следующем пересчёте; оплаченные строки и журналы не меняются. Ссылка под ингредиентами передаёт в покупки выбранный день/неделю и вид плана. Обычный вход в покупки рассчитывает весь месяц; область расчёта подписана над кнопкой.

Ручные открытые позиции с совместимыми единицами покрывают потребность; автоматически добавляется лишь остаток. Несовместимые штуки/граммы без подтверждённого коэффициента не складываются: вместо второй автоматической строки выводится просьба проверить ручное количество/единицу. Без явного подтверждения замены целый суп не считается картофелем, а бульон — отварным мясом, даже если раньше было сохранено такое соответствие. Ошибочный выбор помечается; корректный автоматический запас продолжает учитываться.

Новая миграция не требуется: используются существующие `get_kitchen_state`, `product_save`, `shopping_save`, версии строк и семейные серверные проверки. Согласование выполняется последовательными RPC, а не одной транзакцией; при сетевой ошибке нужно повторить пересчёт, он читает свежие данные и продолжает без умножения строк. Старые `source=generated` и новые UUIDv8 с префиксом `a17e` считаются управляемыми расчётом (существующий RPC записывает новые строки как `source=manual`). Остальные ручные строки не отменяются и их количество не переписывается. Детерминированные ID включают семью, месяц, продукт, единицу и цикл истории покупок; ID оплаченной покупки не переиспользуется. Web Locks упорядочивает пересчёт в нескольких вкладках, версии защищают от устаревшей записи на разных устройствах. Прямое старое SQL-действие `shopping_generate` сохранено для совместимости, новый интерфейс его не вызывает.


## Подтверждение приготовления с заготовками — миграция 016

Для этой функции необходимо применить `supabase/migrations/202611060016_cooking_sources.sql` к реальному проекту Supabase после предыдущих миграций. Публикация GitHub Pages обновляет только интерфейс и не применяет SQL. В среде разработки административные реквизиты Supabase не настроены; локальные SQL-проверки не означают обновления рабочей базы.

Окно подтверждения использует сохранённый подбор из меню, показывает источник и фактическое количество к списанию. Источник можно уточнить для текущего приготовления. Заготовка с бульоном в мл используется напрямую; для порций требуется подтверждённый коэффициент, например 800 мл/порцию. Один источник распределяется между ингредиентами без повторного зачёта. Нулевая строка остаётся явным отказом от расхода, «по вкусу» не списывается автоматически.

Новое действие `cook_confirm_sources` выполняется в одной транзакции `kitchen_mutate`: семейная блокировка и право редактирования, версии меню/задачи и заготовок, проверка положительных количеств, единиц, покрытия расхода и непросроченных остатков; затем прежнее серверное подтверждение продукта/порций и списание заготовок. Любая ошибка откатывает всё приготовление. Ключ операции защищает от повторного списания. Для ингредиента из заготовки пишется движение «Ингредиент блюда» и источник в `cooking_events.usage`; `preparation_uses` не создаётся, поскольку эта таблица означает использование целого готового блюда и участвует в подсчёте выполненных пунктов меню. Исходные ингредиенты заготовки повторно не списываются. Источники и их названия в истории подтверждает сервер.

Старый `cook_confirm` остаётся совместимым. До применения 016 интерфейс может подтвердить приготовление только из продуктов через прежний RPC, с правильными фактическими названиями выбранных продуктов. Попытка списать заготовку останавливается с объяснением о серверном обновлении; частичных операций нет. Признак установленной функции — `schema_version >= 16` из `get_kitchen_state`.


## Объединение ингредиентов плана

Потребность меню/плана перед учётом запасов объединяется по нормализованному названию и совместимой единице: регистр, порядок слов, известные синонимы, г/кг и мл/л. Служебные уточнения «для зажарки», «для жарки», «для обжарки», «для подачи», «для смазывания формы/сковороды» и «для тушения» не создают новый продукт. Например, 80,8 мл растительного масла и 67,5 мл масла для зажарки дают одну потребность 148,3 мл. Таблица и пересчёт покупок используют один результат, запас распределяется один раз. Сохранённые старые соответствия с такими уточнениями продолжают распознаваться.

В таблице и общем подборе один продукт имеет один заголовок даже при несовместимых единицах: кукуруза 150 г и 1,5 упаковки показывается общей группой с двумя количествами и отдельным выбором источника для каждой единицы. Вес упаковки не предполагается; эти количества не превращаются в выдуманную сумму граммов. Состояние продукта сохраняется: отварное куриное мясо и сырое куриное филе остаются разными ингредиентами. Это изменение интерфейса и общего клиентского расчёта, дополнительной миграции БД не требует.


## Автоматический пересчёт ложек и массы

При подборе запасов мерная чайная ложка считается 5 мл, столовая — 15 мл. Для распознанных обычных продуктов используются ориентировочные плотности: мелкая поваренная соль 1,2 г/мл (6 г/ч. л.), сахар-песок 0,8 г/мл (4 г), пшеничная мука 0,6 г/мл (3 г), растительное/подсолнечное/оливковое масло 0,92 г/мл (4,6 г), вода 1 г/мл (5 г), молоко 1,03 г/мл (5,15 г), жидкий мёд 1,4 г/мл (7 г). Значения относятся к ложке без горки и подписаны как ориентировочные. Крупная/морская соль, неизвестные продукты, вес штуки/упаковки, объём стакана и порции автоматически не предполагаются.

При совпадении продукта пересчёт применяется сразу: 1,125 ч. л. соли соответствует примерно 6,75 г; запас 190 г покрывает потребность без ручного ввода. В источнике значение предзаполнено в удобном направлении «Сколько г в 1 ч. л.». Пользователь может изменить его; сохранённый ручной коэффициент и «Не учитывать» имеют приоритет, сброс возвращает справочное значение. Разные единицы нескольких запасов распределяются с собственными коэффициентами, без повторного зачёта.

Покупки используют тот же расчёт, недостающее количество ложек переводится в физическую единицу г/мл. Подтверждение приготовления передаёт фактический расход в совместимой физической единице: например 6,75 г соли, без округления коэффициента 1/6 до четырёх знаков. Снимок рецепта сохраняет исходную меру. Существующий серверный контракт и его проверки не меняются; приготовление с заготовками по-прежнему требует ранее подготовленную миграцию 016, дополнительной миграции для автопересчёта нет.


## Ручная замена ингредиента другой заготовкой

В списке источников доступны все положительные непросроченные заготовки семьи. При несовпадающем названии/составе можно выбрать заготовку и отметить «Подтверждаю замену ингредиента … этой заготовкой». До подтверждения источник не учитывается; автоматический подбор по-прежнему не предлагает суп вместо картофеля. Это явная замена по решению пользователя, а не расчёт количества картофеля в супе. Для разных единиц дополнительно требуется коэффициент, например 300 г заменяемого ингредиента на одну порцию заготовки.

Подтверждение сохраняется вместе с соответствием и коэффициентом в настройках подбора данного браузера/аккаунта/семьи. Изменение коэффициента не снимает подтверждение; смена источника требует нового решения. Правка в окне подтверждения готовки действует для текущего приготовления. Общий подбор, таблица и фактический расход используют одно решение. Остаток заготовки распределяется один раз между ингредиентами, нехватка и устаревшая версия проверяются сервером.

Новая миграция не нужна; реальное списание заготовок при готовке требует ранее подготовленную 016. Для использования уже готового блюда целиком остаётся операция «Использование» в разделе «Заготовки», со связью с пунктом меню: она не означает замену отдельных ингредиентов и не списывает их заново.


## Готовое блюдо вместо повторного приготовления

В подтверждении доступны два режима: «Готовлю из ингредиентов» и «Использую готовую заготовку». Если одна заготовка этого же рецепта назначена всем количественным ингредиентам, окно предлагает второй режим сразу; при частичной общей привязке показывает подсказку: готовый суп не нужно отдельно расходовать на картофель, морковь и лук. В первом режиме каждое количество является отдельным расходом, поэтому общий остаток может закончиться; проверка нехватки не отключается и одна порция не засчитывается несколько раз.

Для готового блюда выбирается положительная непросроченная заготовка семьи, связанная с рецептом пункта меню; пользователь указывает её фактическое количество и дату. Для порций первоначально предлагается не больше остатка и запланированных порций, оба числа показаны; г/мл не превращаются в порции без явного ввода. Подтверждение вызывает один существующий `prep_use` с `reason=Использование` и `menu_id`. Сервер атомарно уменьшает остаток, пишет `preparation_uses` и движение, отмечает одно выполнение меню и первую активную связанную задачу. Ингредиенты, `cooking_events` и новые выходные заготовки не создаются. Ключ операции общий для модального окна, версии и семейные проверки сохраняются. На время отправки переключение режимов и закрытие заблокированы, введённые значения сохраняются при переключении режимов.

В отдельной задаче без меню или не первой активной связанной задаче прямое использование недоступно: предлагается открыть меню, чтобы не отметить другую задачу вместо выбранной. Миграция 016 для использования готового блюда не нужна: применяется ранее существующий контракт `prep_use` из 008. Для списания заготовки как отдельного ингредиента при новой готовке прежняя необходимость 016 сохраняется.


## Дополнительный бульон при использовании супа — миграция 017

В режиме «Использую готовую заготовку» для супов и рецептов с бульоном есть опция «Добавляю бульон к заготовке супа». Она включается пользователем: если бульон уже списан при приготовлении, повторного автоматического расхода нет. Выбираются отдельная непросроченная заготовка бульона и её фактическое количество. Для супа в порциях предлагается доля бульона из снимка рецепта на выбранные порции: 1200 мл на 4 порции дают 600 мл на 2. Сохранённый коэффициент для бульона в порциях переиспользуется. При неизвестном переводе или супе в граммах/мл количество вводится явно; ручная поправка не перезаписывается при изменении порций. Остаток бульона после использования показан перед подтверждением.

Для совместного расхода необходимо применить `202611070017_preparation_broth.sql` после 016. В текущей облачной среде административного доступа к Supabase нет; GitHub Pages не применяет SQL. До обновления включённое дополнительное списание блокируется до любого запроса, оба остатка сохраняются. Обычное использование супа без добавления бульона продолжает работать через прежний `prep_use`.

Миграция расширяет существующий приватный складской обработчик, сохраняя контракт категорий. Один `kitchen_mutate(prep_use)` с `additional_broth` и явным подтверждением расходует оба источника в одной транзакции: права семьи, разные ID, версии, единица и остаток бульона, сроки годности и исходные проверки супа/меню. Бульон получает запись использования без `menu_id`; суп отмечает одно выполнение меню и одну первую связанную задачу. Новых приготовлений или выходных заготовок нет. При ошибке в любом источнике всё откатывается, одинаковый ключ операции не повторяет списание. Ранее выполненные использования и остатки задним числом автоматически не переписываются.
